# X3 / FA61 protocol target

This page is the model-level entry point for devices that enumerate as USB PID `0xfa61` in the driver's `x3-wired` mode. Packet definitions live in [`../protocols/`](../protocols/README.md); transport behavior lives in [`../transports/`](../transports/README.md).

## Identity and aliases

Tested or analyzed hardware may be sold as Attack Shark X3, FA61, or Kysona M600. They are treated as one protocol target for now, but branding alone does not prove identical firmware behavior.

The BLE names `M600-5.2` and `M600-5.4` identify RF/host slots, not firmware versions. Both strings occur in the same firmware payload; `NVDS_TAG_RF_MODE` selects the advertised name. A short pairing-button press toggles slots and a long press enters pairing for the selected slot. See the [BLE transport reference](../transports/ble-gatt.md#device-identity) and [correction ledger](../research/corrections.md).

The same X3/M600 packet dialect is also reachable through the 2.4 GHz receiver,
which enumerates as PID `0xfa60`. The receiver PID is a transport identity, not
proof of the paired mouse model; the Rust receiver path is therefore explicitly
selected as X3 rather than inferred from `0xfa60` alone.

## Device-specific caveats

- Button mapping writes a complete table. The native Rust CLI reads the selected target table and changes only the requested safe slot through a bounded-slot delta; all other slots are preserved unchanged. The CLI exposes left, right, middle, DPI, forward, and backward slots with safe symbolic actions (disable, left-click, right-click, middle-click, backward, forward, double-click, dpi-cycle, dpi-plus, dpi-minus, profile-cycle, profile-plus, profile-minus, fire-button, scroll-up, scroll-down, the media and browser families, and the stock shortcut presets). Easy Aim, the wheel slots (indices 4 and 5), and arbitrary raw action codes are intentionally not exposed.
- Hardware without an RGB base shows no visible response to RGB fields. Sleep, deep-sleep, and light-field semantics remain incompletely characterized on X3.
- Report `0x05` with light-mode byte `0x00` was accepted over USB and BLE on the same physical X3/M600 mouse during the 2026-07-22 corrected probe, including subsequent BLE commands and reconnect. The earlier crash report is historical and unresolved; follow the conservative guard in [`../safety.md`](../safety.md).
- Reset must use the model-correct report sequence and conservative delays. Stock X3 captures use roughly 500 ms between reports.
- Reports `0x04`, `0x05`, and `0x08` are target-profile operations on X3/M600. Their armed read selectors can load another working profile without changing persistent `0x0c` metadata. The 2026-07-17 X3/M600 “metadata-only” result was corrected after this branch was recovered.
- The physical DPI button is a separate auxiliary input report (`03 00 10 <active-stage> 00`), not an extra normal mouse-button bit. Byte 3 is decoded as the resulting one-based active DPI stage; profile-separated captures observed stages 2 and 3.
- The stock profile-1 DPI configuration sets stage 6 to 26,000 DPI (the maximum supported value). This is the factory default confirmed by 2026-07-24 capture; the stock software appears to showcase the sensor's ceiling in the top stage.
- The FA60 receiver emits a periodic 5-byte battery report `03 10 40 01 <level>` on endpoint `0x83` (level 1–10, ×10 = percentage). Confirmed by X3.exe disassembly and live capture (2026-07-24: `03 10 40 01 0a` = 100%). The firmware suppresses this report while charging; all other 2.4 GHz paths (commands, pointer, DPI button) remain active. See [battery doc](../protocols/battery.md). \[disassembly + live-confirmed 2026-07-24]

## Reusable X3/M600 profile A/B probe (historical tooling)

The probing sessions documented in [`../evidence/x3-fa61/`](../evidence/x3-fa61/README.md#probing-sessions-2026-07-17) were driven by the now-deleted TypeScript script `scripts/fa61-profile-ab.ts`. The script reference is provenance only — the raw JSON captures are the authoritative evidence.

The script ran the same guarded FA61 Col04 experiment against either mouse, defaulting to 500 ms after every HID selector or write, snapshotting reports `0x0b`, `0x0c`, `0x04`, `0x05`, and `0x08`, and supplying the intended one-based profile target on every `0x04`/`0x05`/`0x08` read and write.

Correctly targeted 2026-07-17 runs succeeded on both tested mice: profiles 1 and 2 loaded distinct DPI images under software selection and after power-cycle, and one physical Forward press bound to `34 00 00` changed profile 1 to profile 2. The runner treated malformed armed-read observations as transient and restored DPI, preferences, and button reports after an unexpected error.

Equivalent experiments can be reproduced using the Rust `x3ctl` CLI (`cargo run -p x3ctl -- ...`).

## Readback latency benchmark (historical tooling)

The readback latency benchmark documented in [`../evidence/x3-fa61/`](../evidence/x3-fa61/README.md#probing-sessions-2026-07-17) was driven by the now-deleted TypeScript script `scripts/fa61-readback-benchmark.ts`. The script reference is provenance only — the raw JSON captures are the authoritative evidence.

The script performed validated, read-only `0x0b`, `0x0c`, `0x04`, and `0x08` transactions with both a persistent HID handle and one handle per transaction.

A conservative preliminary A/B used five warm-ups and twenty measured transactions per
report and per mode. With a persistent handle, both mice had approximately 2 ms median
selector SET time, 3 ms to complete the first ready-status read, and 3 ms target GET
time. Neither mouse was consistently faster. Opening a handle had a median cost of
roughly 7–8 ms for X3 and 10–11 ms for M600 in these sequential sessions, but that
host-side difference is not evidence of faster mouse firmware.

**Live-confirmed on M600, 2026-07-17:** the 43 measured profile-metadata attempts
included three malformed packets with header `0c 0a 02 ...` and valid complements. The
initial X3 session also returned three version packets with prefix `0b 08 02` among 40
measured version reads. A repeated X3 strict-validation session observed one version
rejection (caused by an opened-but-then-erroring handle, not a publication race) across
160 measured transactions and no further cross-report contamination. The M600 publication
race is reproducible at this sample size; the X3 was clean once warm-up had drained any
leftover mailbox state. The X3 cross-report evidence must not be reported as an
independent fault.

Raw benchmark and session JSON is archived under
[`../evidence/x3-fa61/`](../evidence/x3-fa61/README.md#probing-sessions-2026-07-17).


## Production implementation gaps

The native Rust codec emits the capture-confirmed, model-correct 16-bit big-endian checksums for reports `0x05` and `0x08`. The historical TypeScript builders were removed during the Rust-only cutover; retained captures and evidence documents preserve their provenance and known legacy X11 checksum behavior.

## Evidence and open questions

Raw X3/FA61 evidence is catalogued under [`../evidence/x3-fa61/`](../evidence/x3-fa61/README.md). Analysis provenance and dated experiments live under [`../research/`](../research/README.md).

Open questions include timing bounds for serialized edge-triggered profile changes, native access to an already bonded BLE device, sleep/deep-sleep behavior, and full multi-page `0x09` macro behavior over BLE. Profiles 3–5 and multi-step physical cycling (cycle/plus/minus) were confirmed end-to-end on 2026-07-25. An ACK or matching report-`0x0c` metadata readback proves metadata acceptance, not completion of deferred profile application or persistence.
